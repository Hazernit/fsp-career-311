# API ФСП Карьера

Полная машиночитаемая спецификация OpenAPI 3.1 находится в [public/openapi.json](../public/openapi.json) и обслуживается по `/openapi.json`. Базовый адрес API — `/api`. Все даты ISO UTC, зарплата — целые рубли за месяц. POST/PATCH принимают `Content-Type: application/json`; изменения отправляйте с того же Origin. Сессия — HttpOnly cookie `fsp_session`.

Успех: `{"data": ...}`. Ошибка: `{"error":{"code":"VALIDATION_ERROR","message":"..."}}`. Основные статусы: 400 неверные поля, 401 нет сессии/неверный вход, 403 другая роль/email не подтверждён/Origin, 404 отсутствующая или чужая запись, 409 конфликт состояния, 413 тело больше 64 КиБ, 415 не JSON, 429 частота, 503 почта не настроена. Создание анкеты, потребности, приглашения и вакансии возвращает 201, остальные JSON-действия — 200. Неавторизованный клиент не получает контактные поля даже в ошибке.

## Общие методы и авторизация

| Метод | Адрес | Доступ и результат |
| --- | --- | --- |
| GET | `/meta` | Публичные категории, версии, режим демо и примеры синтетического реестра |
| GET | `/session` | Текущий пользователь или null; допускает ожидающий подтверждения аккаунт |
| POST | `/auth/register` | `{email,password,role,name,consentProcessing:true}`; пароль 10–128 символов; создаёт ожидающую сессию |
| POST | `/auth/login` | `{email,password}`; устанавливает сессию своей неизменяемой роли |
| POST | `/auth/verify` | `{token}`; одноразовая ссылка до 24 часов, подтверждает email |
| GET | `/auth/confirmation` | Только свой ожидающий аккаунт; в демо возвращает confirmationUrl, в обычном режиме токен не выдаёт |
| POST | `/auth/resend` | Повторная отправка из своей ожидающей сессии, до трёх запросов за 15 минут |
| POST | `/auth/logout` | Удаляет текущую сессию |
| POST | `/auth/demo` | Только в демо; `{role,fresh?}` создаёт или восстанавливает свою демо-пару браузера |

На локальном стенде `demo-outbox` показывает ссылку только собственной ожидающей сессии. До подтверждения регистрация не даёт доступ к профилю, анкетам, тестам и кабинетам. Неверный, использованный или истёкший токен не подтверждает email. Реальная отправка через Resend требует собственных `RESEND_API_KEY` и `EMAIL_FROM`; её доставка в этой проверке не выполнялась.

## Профиль и проверка компетенций

| Метод | Адрес | Доступ и результат |
| --- | --- | --- |
| GET/PATCH | `/profile` | Собственный профиль подтверждённого аккаунта; строгий список разрешённых полей |
| GET | `/profile/pdf` | Собственный стандартный профиль кандидата с контактами и историей |
| POST | `/fsp/link` | Кандидат; `{fspId,proofCode}`, только совпадение с mock-fsp |
| POST | `/fsp/unlink` | Кандидат; убирает связь и синтетическую историю |
| POST | `/questionnaires` | Кандидат с согласием на обработку; `{industry,specialization,claimedGrade}`, сохраняет новую неизменяемую запись |
| GET | `/questionnaires/history` | Все собственные записи анкет, новые первыми; другой кандидат их не получает |
| POST | `/tests/start` | Кандидат; `{specialization,grade}` после соответствующей последней анкеты; сохраняет приватный вариант, отдаёт вопросы без эталона и seed |
| GET | `/tests/current` | Своя действующая попытка или null |
| POST | `/tests/{id}/submit` | Кандидат-владелец; `{answers:{questionId:optionId}}`, серверный результат и разбор |
| GET | `/tests/history` | До 100 своих завершённых/истёкших попыток |

Кандидат может изменять name, title, city, phone, bio, skills, roles, softSkills, experienceYears, industry, specialization, claimedGrade, consentProcessing, consentPublication, isPublic. Работодатель — company, website, description, contactName, contactEmail, contactMethod. `skills`, `roles` и `softSkills` — массивы до 30 непустых строк по 80 символов; пробелы по краям убираются, дубли объединяются. Роли и софт-скиллы остаются сведениями, указанными кандидатом, и включаются в автоматический PDF. Неизвестные поля отклоняются; verifiedGrade, demonstratedSkills, testScore и fspVerified нельзя изменить этим методом. При отозванном согласии на публикацию или обработку публичность выключается. Отзыв обработки возвращает работодателям 404 для карточки и PDF даже после принятия приглашения или отклика; contacts в ранее принятом приглашении становится null. Отзыв только публикации сохраняет ранее согласованный доступ, пока согласие на обработку действует. До разрешения контакта email, телефоны и явные Telegram-контакты скрываются также в свободном тексте, roles и softSkills, включая PDF и рекомендации.

Ответ анкеты: `{id,industry,specialization,claimedGrade,createdAt}`. Отрасль обязательна и содержит 1–120 символов, специализация — backend/frontend, предполагаемый грейд — junior/middle. Анкета обновляет отрасль и самооценку профиля, но не меняет подтверждённый грейд или специализацию. История дополняется новой записью, API перезаписи или удаления прошлых ответов отсутствует. Ограничение — 30 записей за час на кандидата. Перед началом теста сервер сверяет последнюю собственную анкету с requested specialization/grade и непустой отраслью; иначе возвращает 409 `QUESTIONNAIRE_REQUIRED`. Передавать questionnaireId не нужно. Ссылка на соответствующую анкету хранится в новой попытке на сервере; старые тесты остаются читаемыми после миграции.

Тест содержит 12 вопросов, максимум 600 секунд. Неизвестные ID ответов отклоняются, пропущенные вопросы считаются неправильными. Порог — 75% и ≥1 правильного из двух по каждой компетенции. Навык продемонстрирован при 2/2. Первый провал Middle не блокирует тест Junior и не присваивает его автоматически. Новый тест той же категории после завершения — не чаще раза в 10 минут; смена подтверждённой категории — через 90 дней.

## Работодатель и приглашения

| Метод | Адрес | Доступ и результат |
| --- | --- | --- |
| GET/POST | `/demands` | Только собственные потребности работодателя |
| GET | `/demands/{id}` | Только владелец; описание и сохранённая исходная подборка |
| POST | `/demands/{id}/match` | Только владелец; первый снимок, категории, версия алгоритма; последующие вызовы не перезаписывают его |
| GET | `/candidates` | Работодатель; фильтры specialization, grade, skills через запятую, fspOnly=true; опубликованные подтверждённые профили с ранжированием внутри категории |
| GET | `/candidates/{id}` | Работодатель; публичный профиль, contactUnlocked и contacts|null по разрешению этой компании |
| GET | `/candidates/{id}/pdf` | Тот же доступ к профилю и контактам в PDF |
| GET | `/invitations` | Свои входящие у кандидата, свои исходящие у работодателя |
| POST | `/invitations` | Работодатель; candidateId, demandId?, salaryFrom, salaryTo, description, contactMethod |
| POST | `/invitations/{id}/respond` | Только приглашённый кандидат; decision=accepted или declined, терминальный статус неизменяем |

Потребность содержит title, description, specialization, grade, skills, mustHave, industry?, salaryFrom?, salaryTo?. Навыки из словаря описания дополняют явно введённые. mustHave проверяются среди продемонстрированных навыков. Все зарплатные пары должны быть целыми числами: от > 0, до ≥ от, до ≤ 10 000 000. Зарплата обязательна для приглашения и опубликованной вакансии.

Подбор возвращает `{demand,original,categories,algorithmVersion,originalCount}`. Каждая рекомендация содержит score, scoreBreakdown, testScore, achievementBonus, reasons, gaps, matchedSkills, отдельно skills и demonstratedSkills. Это сравнительный балл, а не вероятность найма. Перед чтением снимка актуальная приватность применяется снова, поэтому список может сокращаться после отзыва публикации.

Общий каталог сгруппирован по подтверждённой специализации и грейду, а внутри категории сортируется по `score` убыванию и стабильному ID при равенстве. Здесь `score = 95 × testScore / 100 + achievementBonus`, ФСП даёт максимум 5 баллов только за verified-достижения по продемонстрированным навыкам; неподтверждённые, нерелевантные и будущие результаты бонуса не дают. `rankingScope=category`, `rankingVersion=fsp-category-evidence-1.0.0`. Стаж, самооценка, роли, софт-скиллы и количество заявленных навыков не повышают балл каталога. Его балл не является оценкой соответствия конкретной потребности; её алгоритм и сохранённая исходная подборка остаются отдельными.

## Вакансии и отклики

| Метод | Адрес | Доступ и результат |
| --- | --- | --- |
| GET | `/vacancies` | Подтверждённый аккаунт; опубликованные вакансии, у кандидата applied |
| POST | `/vacancies` | Работодатель-владелец; `{demandId}`, публикация потребности с зарплатой |
| POST | `/vacancies/{id}/apply` | Кандидат; сохраняет отклик и разрешает контакт только работодателю этой вакансии |
| GET | `/applications` | Свои исходящие отклики кандидата или входящие отклики работодателя с текущим статусом |
| POST | `/applications/{id}/status` | Только работодатель-владелец; `{status:viewed\|accepted\|declined}`, возвращает обновлённый отклик |

Отклик содержит `{id,vacancyId,employerId,candidateId,company,title,candidateName,salaryFrom,salaryTo,status,createdAt,updatedAt}`. Контакты не дублируются: работодатель получает их отдельным авторизованным запросом `/candidates/{id}` с проверкой актуального согласия. Первичный статус — `sent`; возможны `sent → viewed/accepted/declined`, `viewed → accepted/declined`. `accepted` и `declined` окончательны; смена возвращает 409 `APPLICATION_FINAL`, повтор уже установленного статуса возвращает ту же запись. Кандидат меняет статус только приглашения, статус отклика ему доступен для чтения. Чужой работодатель получает 404, кандидат при попытке изменения — 403. Повторный отклик не создаёт дубль и не сбрасывает решение. При отзыве обработки данных candidateName в списке работодателя очищается от контактоподобного текста.

## Пример работы с API

Следующий пример использует вымышленную демо-личность и локальный стенд. Cookie-файл содержит токен доступа; храните его как секрет и удалите после проверки.

```sh
curl -c /tmp/fsp-cookie -H 'Content-Type: application/json' \
  -d '{"role":"employer"}' http://127.0.0.1:5173/api/auth/demo
curl -b /tmp/fsp-cookie http://127.0.0.1:5173/api/candidates?specialization=backend
```

В браузере тело регистрируемого кандидата:

```json
{"email":"candidate@example.org","password":"MyLongPass123","role":"candidate","name":"Участник","consentProcessing":true}
```

Ответы теста собираются из ID предъявленного экземпляра. Сервер не принимает номер позиции как ключ ответа; семена и эталоны не являются публичным контрактом. Чужие ID потребностей, тестов и приглашений дают одинаковое сообщение об отсутствии записи, без подтверждения её существования.

Проверка `node --test tests/domain.test.ts tests/migrations.test.ts` проверяет банк, ранжирование и сохранность существующих данных при SQL-миграции. `npm run test:api` выполняет сквозные локальные HTTP-проверки с собственными сессиями. Для контейнера используйте `FSP_BASE_URL=http://127.0.0.1:8080 FSP_DATA_DIR=/data node tests/api-integration.mjs` внутри контейнера; при отдельной локальной структуре D1 задайте `FSP_TEST_D1_DIR`. Эталонные ответы читает только тестовый процесс из собственного локального SQLite-хранилища. Проверка подтверждает механизмы сервера, а не психометрическую валидность или надёжность оценивания реальных людей.
