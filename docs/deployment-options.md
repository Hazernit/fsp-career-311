# Размещение ФСП Карьеры: локальный стенд и будущая VM

Сейчас решение запускается локально через [compose.yaml](../compose.yaml). Публичное размещение приложения и покупка облачных ресурсов не выполнялись. Эта инструкция — подготовка будущего демонстрационного стенда в Яндекс Облаке; она не объявляет текущий образ готовым промышленным сервисом. Источники проверены 10 октября 2026 года.

## Выбор размещения

| Вариант | Для чего подходит | Что требуется |
| --- | --- | --- |
| Локальный Docker | Проверка жюри, разработка, запись демонстрации | Docker Compose, постоянный том `/data`; вход через localhost |
| Одна Compute Cloud VM + Caddy | Будущий небольшой демонстрационный стенд по HTTPS | Постоянный диск, домен, резервные копии, проверка поведения за прокси |
| Промышленный сервис | Реальные пользователи, эксплуатация и масштабирование | Отдельная доработка runtime и БД, почты, ФСП, мониторинга и восстановления |

Для небольшой демонстрации рекомендуем Linux VM **2 vCPU, 4 ГБ RAM, 20–40 ГБ сетевого SSD** и статический публичный IP. Это инженерная стартовая оценка, а не результат нагрузочного теста в облаке. Для предсказуемого отклика выбирайте гарантированную долю CPU 100%; сборку образа удобнее выполнять заранее, чем расходовать память VM. Docker поддерживается официальным сценарием [запуска контейнера на Compute Cloud VM](https://yandex.cloud/en/docs/tutorials/infrastructure-management/run-docker-on-vm/console).

Текущий [docker-start.mjs](../scripts/docker-start.mjs) запускает `wrangler dev --local`: Worker выполняется в локальном эмуляторе, а D1/SQLite хранится в `/data`. Постоянный Docker volume переживает замену контейнера, но остаётся на диске своего Docker-хоста и сам по себе не является резервной копией. [Docker: volumes](https://docs.docker.com/engine/storage/volumes/).

Прямой перенос этого образа в Yandex Serverless Containers не рекомендуем: содержимое ephemeral-диска не гарантируется между вызовами и удаляется после завершения экземпляра. Локальная SQLite не должна быть единственным источником данных в таком runtime. Монтирование Object Storage не заменяет транзакционную БД. [Yandex: ephemeral disk](https://yandex.cloud/en/docs/serverless-containers/concepts/mounting#mount-ephemeral-disk).

## Что подготовить перед будущим запуском

1. Выбрать VM, сетевой SSD и статический IP; настроить SSH по ключу. Установить Docker Engine и современный Compose; для приложенного override требуется Compose **2.24.4 или новее**. Проверить `docker compose version`.
2. Настроить DNS-запись `A` домена на IP VM. `AAAA` добавлять только при действительно работающем IPv6. Для автоматического сертификата Caddy нужны правильный DNS, доступные порты TCP 80/443 и постоянный каталог сертификатов. [Caddy: automatic HTTPS](https://caddyserver.com/docs/automatic-https).
3. В группе безопасности открыть TCP 80/443 для пользователей, TCP 22 только с административного IP; UDP 443 нужен при использовании HTTP/3. Разрешить необходимый исходящий доступ для DNS, обновлений и ACME. Порт приложения 8080, Docker API и административный порт Caddy наружу не открывать. [Yandex: security groups](https://yandex.cloud/en/docs/vpc/concepts/security-groups).
4. Перенести проверенный commit/tag, заранее собрать либо доставить соответствующий образ и сохранить его идентификатор. Один экземпляр приложения владеет локальным томом; горизонтальное масштабирование с этой БД не настроено.

### Сохранение существующих данных

HTTPS-конфигурация расширяет базовый Compose. Она использует **тот же** логический том `fsp-data`, но требует явного фактического Docker-имени через `FSP_DATA_VOLUME`. Если имя неверно или том отсутствует, запуск должен завершиться ошибкой, а не создать пустую базу.

Из корня репозитория приложения, где находится `compose.yaml`, найдите контейнер и имя его тома:

```sh
docker compose -f compose.yaml ps -q career
# Подставьте выведенный ID вместо CONTAINER_ID:
docker inspect CONTAINER_ID --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}'
docker volume inspect ACTUAL_VOLUME_NAME
```

Обычно при стандартном имени проекта это `platform_fsp-data`, но полагаться на это без проверки нельзя. На новой VM сначала создайте выбранный постоянный том (`docker volume create fsp-career-data`) или восстановите в него согласованную копию. Перенос исходников не переносит содержимое тома. Перед копированием SQLite остановите приложение и сохраните весь `/data`, включая служебные файлы; затем проверьте восстановление отдельно. Не используйте `down -v` или `volume prune` для рабочего стенда.

### Конфигурация HTTPS

Создайте локальный игнорируемый Git файл `.env.https`. Значения ниже — примеры, их нужно заменить:

```dotenv
FSP_DOMAIN=career.example.com
FSP_TLS_EMAIL=admin@example.com
FSP_DATA_VOLUME=ACTUAL_VOLUME_NAME
CADDY_IMAGE=caddy:2-alpine
```

Перед реальным размещением закрепите проверенную версию либо digest официального Caddy-образа. Приложенные [docker-compose.https.yml](../deploy/docker-compose.https.yml) и [Caddyfile](../deploy/Caddyfile) сохраняют `/data` и `/config` Caddy, публикуют только HTTPS-прокси и обращаются к `career:8080` по сети Compose. Схема соответствует [официальному примеру Caddy + Docker Compose](https://caddyserver.com/docs/running#docker-compose). Объединение и все относительные пути считаются от первого файла `compose.yaml`. [Docker: merge files](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/).

Проверка конфигурации не запускает сервисы и не покупает ресурсы:

```sh
docker compose --env-file .env.https -f compose.yaml -f deploy/docker-compose.https.yml config
```

После отдельного решения разместить стенд и устранения ограничения runtime ниже команда запуска на VM будет такой:

```sh
docker compose --env-file .env.https -f compose.yaml -f deploy/docker-compose.https.yml up --build -d
docker compose --env-file .env.https -f compose.yaml -f deploy/docker-compose.https.yml logs --tail=100 career caddy
```

### Обязательная проверка URL за прокси

Caddy сохраняет исходный `Host` и передаёт `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-For`; он не должен подменять клиентский `Origin` внутренним HTTP-адресом. [Caddy: proxy headers](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults).

Текущий сервер в [security.ts](../lib/server/security.ts) сравнивает `Origin` с `request.url`, а `Secure` у cookie выбирает по HTTPS-схеме этого URL. Поэтому **одного reverse proxy недостаточно для объявления HTTPS-запуска проверенным**: выбранный runtime должен восстановить внешнюю HTTPS-схему и Host только от доверенного прокси. Работа текущего Wrangler local за этим Caddy ещё не проверена. Если Worker видит `http://career:8080`, нужно исправить runtime/адаптер до открытия стенда; нельзя отключать Origin-проверку, переписывать Origin или снимать `Secure` ради обхода ошибки.

Перед публикацией проверьте по внешнему HTTPS-домену: демо-вход и POST создания потребности проходят; `fsp_session` и `fsp_demo_pair` имеют `HttpOnly`, `SameSite=Lax`, `Secure`; чужой Origin отклоняется; ссылка подтверждения email ведёт на этот же HTTPS-домен; контакты остаются закрыты до разрешённого действия и закрываются при отзыве обработки. После перезапуска контейнера профиль и приглашения должны сохраняться. Отдельно подтвердите восстановление из резервной копии.

## Стоимость: формула вместо обещания тарифа

Для 30 дней непрерывной работы берите `H = 720` часов:

```text
Стоимость = H × (2 × ставка vCPU + 4 × ставка RAM + ставка активного IP)
          + D × ставка SSD за период
          + хранение резервных копий + платный исходящий трафик
          + домен + дополнительные выбранные сервисы.
```

`D` — 20–40 ГБ. Если SSD указан за ГБ·час, его строка равна `H × D × ставка`; если за ГБ·месяц — `D × ставка` за полный месяц. В [официальном примере Compute Cloud](https://yandex.cloud/ru/docs/compute/pricing) для Linux Intel Ice Lake указаны 1,24 ₽ за vCPU·час при 100% и 0,33 ₽ за ГБ RAM·час; пример [VPC](https://yandex.cloud/ru/docs/vpc/pricing) указывает 0,26352 ₽ за активный IP·час. Производный расчёт для 2 vCPU/4 ГБ — **2 736 ₽ вычисления + примерно 190 ₽ IP за 30 дней**, ещё без SSD, копий и домена. Это расчёт по опубликованным примерам, а не персональное коммерческое предложение; перед покупкой сверяйте платформу, гарантированную долю CPU, регион, валюту и ставки в [калькуляторе Yandex Cloud](https://yandex.cloud/ru/prices). Рублёвые цены документации включают НДС. Ставка SSD в доступном текстовом представлении не подтверждена, поэтому полный чек здесь не фиксируем.

При остановке VM вычисления перестают начисляться, но диски, снимки и зарезервированный IP могут продолжать тарифицироваться. Учтите это при оценке короткой демонстрации. [Compute Cloud billing](https://yandex.cloud/en/docs/compute/pricing), [VPC billing](https://yandex.cloud/en/docs/vpc/pricing).

## Переход к промышленному размещению

Для Compute Cloud нужен отдельный серверный runtime на Node и адаптер хранилища: например, PostgreSQL с миграциями и транзакциями либо поддерживаемая SQLite для небольшого одиночного сервера с резервированием. Текущий D1-код нельзя автоматически направить в другую БД одной переменной окружения. Альтернативный путь — native Worker с настоящей привязкой Cloudflare D1; это другой вариант размещения, а не Яндекс Serverless с файлом SQLite.

После выбора пути потребуются реальная доставка email, настоящий проверяемый адаптер ФСП, параметры аутентификации для эксплуатации, мониторинг, восстановление, проверка миграций и работа с персональными данными. Эти доработки описывают следующий этап; демо-реестр, местный Wrangler и короткие тесты текущего MVP не являются подтверждением готовности к промышленному запуску.

## Проверка приложенных файлов

При подготовке инструкции выполнен `docker compose ... config` с тестовыми несекретными значениями: схема объединяется, путь Caddyfile корректен, прямой порт приложения удалён, внешний том указан явно. Caddy-образ на этой машине отсутствует, поэтому `caddy validate` не запускался и образ не скачивался. HTTPS, ACME и облачный запуск пока не проверены.
