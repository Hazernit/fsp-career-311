# ФСП Карьера

Работодатель описывает потребность и получает объяснимую подборку кандидатов с подтверждённой категорией. Он отправляет приглашение с зарплатой; кандидат принимает его или отказывается. Email и телефон становятся доступны только пригласившей компании после принятия либо работодателю, на чью вакансию кандидат самостоятельно откликнулся.

Репозиторий: https://github.com/Hazernit/fsp-career-311 . Прототип сейчас работает локально через Docker; внешний стенд ещё не опубликован. Для будущего размещения в Яндекс Cloud подготовлены варианты и порядок запуска в [руководстве по размещению](docs/deployment-options.md).

Версия приложения — **1.0.2**. Пакет сдачи и исходный тег — **v1.0.3-hackathon**. Основное видео показывает эту версию с голосом Microsoft Дмитрий; дополнительный короткий обзор относится к предыдущему интерфейсу.

Авторы решения команды «311»: Кривошеин Дмитрий Алексеевич и Ощепков Даниил Юрьевич.

Команда — студенты одной учебной группы Московского Политеха. Роли в проекте: Дмитрий — капитан, продукт, архитектура и серверная часть; Даниил — интерфейс, UX, тестирование и демонстрация.

Рабочий MVP включает Backend на Python и Frontend, уровни Junior и Middle, регистрацию с подтверждением email, профили с ролями и софт-скиллами, отдельные согласия, обязательную анкету и её историю, первичный тест, историю результатов, демо-реестр ФСП, сохранение исходной подборки, приглашения, PDF-профили, публикацию вакансий и отклики со статусами в обоих кабинетах. Общий каталог ранжирует внутри подтверждённой категории по результату теста (до 95 баллов) и релевантной ФСП (до 5); подбор по конкретной потребности сохраняет отдельную объяснимую формулу. Подбор использует словарь требований и прозрачную формулу баллов; ответы теста проверяются по воспроизводимым эталонам. Обе механики выполняются локально на CPU.

## Быстрый запуск через Docker

Требуется Docker с Compose. Из каталога с этим README:

```sh
docker compose up --build -d
```

Откройте http://localhost:8080 . Если порт занят, запустите `FSP_PORT=18080 docker compose up --build -d` и откройте http://localhost:18080 . Контейнер сам применяет миграции в постоянный том `fsp-data`. Синтетический набор создаётся идемпотентно при первом входе в демо или подборе.

```sh
docker compose logs -f career
docker compose down
```

Команда `down` сохраняет том и пользовательские данные. Для публичного стенда настройте HTTPS и обратный прокси; в Compose порт намеренно привязан к `127.0.0.1`. Демо использует локальный эмулятор Cloudflare Worker и SQLite/D1, поэтому установка Cloudflare-аккаунта не требуется.

## Запуск из исходного кода

Для полного набора проверок используйте Node.js 24.19.0 и npm; Node 24 нужен тестовому раннеру с TypeScript и встроенным SQLite. Установочные запросы к npm требуют интернет только при первой загрузке пакетов.

```sh
npm ci --include=dev --include=optional --no-audit --no-fund
npm run build
npm run db:local
npm start -- --port 5173
```

Откройте http://127.0.0.1:5173 . Это собранная версия Worker. Для разработки после первой сборки и миграций можно использовать `npm run dev`; он запускает Vinext с HMR на порту 5173. Одновременно запускайте один сервер на этом порту.

Привязка базы `DB` объявлена непосредственно в `vite.config.ts`. Генерируемые `dist/`, `.wrangler/`, `.vinext/`, зависимости и секреты не являются исходным кодом. Данные локально хранятся в `.wrangler/state`. Переменная `FSP_DATA_DIR` меняет каталог состояния у `db:local` и Docker-старта; обычный `npm start` использует `.wrangler/state`.

## Демонстрационный сценарий

1. Зарегистрируйте кандидата с email и согласием на обработку, подтвердите адрес через явно обозначенный демо-ящик. Для ускоренного знакомства можно выбрать демо-вход.
2. Заполните профиль, роли и софт-скиллы, задайте отдельное согласие на публикацию. Сохраните анкету: отрасль, специализацию и предполагаемый грейд. Предыдущие анкеты остаются в истории; самооценка не присваивает категорию.
3. Пройдите 12 вопросов за максимум 10 минут. Для категории нужны ≥75% и хотя бы один верный ответ в каждой из шести компетенций. Сервер допускает тест только по категории последней собственной анкеты.
4. В кабинете работодателя создайте потребность и обязательные навыки. Изучите исходную подборку и объяснения; фильтры не перезаписывают её. Общий каталог дополнительно показывает рейтинг внутри категории.
5. Отправьте выбранному кандидату приглашение с зарплатой от–до. До принятия контакты закрыты в JSON и PDF, включая Telegram-данные в свободном тексте.
6. Вернитесь к тому же кандидату и примите приглашение. Контакты откроются только этой компании. Для полного пути приглашайте свой подтверждённый демо-профиль; ответ за синтетического кандидата из общего каталога не подделывается.
7. Опубликуйте вакансию из потребности с зарплатой. Кандидат самостоятельно откликается, работодатель видит входящий отклик и меняет статус. Кандидат видит тот же статус в разделе «Отклики»; принятое или отклонённое решение окончательно.

Пара ролей сохраняется за секретным HttpOnly cookie и не смешивается с другими браузерами. `POST /api/auth/demo` с `{"role":"candidate","fresh":true}` создаёт новую пару. Общий каталог содержит 32 вымышленных подтверждённых профиля, по восемь на категорию. Демо-кандидату также доступно входящее приглашение вымышленной компании для проверки принятия и отказа.

## Email и интеграция ФСП

В демо почта не отправляется в интернет. Регистрация создаёт неподтверждённую сессию, а `GET /api/auth/confirmation` показывает ссылку только владельцу этой ожидающей подтверждения сессии. Подтверждение действительно меняет серверное состояние; до него тесты и кабинет закрыты. Экран явно обозначает демонстрационный почтовый ящик.

Для реальной доставки задайте секрет `RESEND_API_KEY`, переменные `EMAIL_FROM` (подтверждённый адрес отправителя) и `DEMO_MODE=false` в окружении Worker. Используется HTTP API Resend. Секреты не храните в Git, клиентском JavaScript и архиве сдачи. Для локального Wrangler они могут находиться в игнорируемом `.dev.vars`; на хостинге задавайте через управление секретами выбранного провайдера. После смены окружения перезапустите сервер. Без ключа и отправителя регистрация в режиме `DEMO_MODE=false` вернёт ошибку конфигурации. При временном сбое доставки существует `POST /api/auth/resend` из ожидающей сессии.

Коды демо-реестра ФСП показаны в форме привязки и `/api/meta`. Известный ID и корректный код подтверждают только синтетическую запись с источником `mock-fsp`. Произвольный ID не проходит проверку. Реальная ФСП, OIDC/Keycloak и связь реального человека с ID не подключены: контракт будущего адаптера описан в [архитектуре](docs/architecture.md).

## Проверки и измерения

Без запущенного сервера:

```sh
npm run typecheck
npm run test:domain
node --test tests/migrations.test.ts
npm run validate
```

При запущенной локальной собранной версии на 5173:

```sh
npm run test:api
node scripts/load-check.mjs
```

Если стенд запущен на другом loopback-порту, задайте `FSP_BASE_URL=http://127.0.0.1:8080`. API-тест намеренно допускает только localhost и читает эталоны из локальной D1-базы; это тестовая привилегия, а не API для пользователей. Для Docker его файловый white-box сценарий требует доступа к тому же каталогу состояния; обычный `npm run test:api` рассчитан на `.wrangler/state` из запуска исходников.

В Docker выполните раннер внутри контейнера с тем же постоянным томом. Рабочий каталог `/data` нужен для записи результатов; исходный `/app` доступен только для чтения:

```sh
docker compose exec --workdir /data -e FSP_BASE_URL=http://127.0.0.1:8080 -e FSP_DATA_DIR=/data career node /app/tests/api-integration.mjs
docker compose cp career:/data/tests/results ./docker-api-results
```

Проверены 4 000 вариантов и 48 000 вопросов, девять доменных/приватностных проверок, две проверки миграций и 22 сценария API и 24 текстовые проверки трёх PDF. На восьми отложенных синтетических потребностях и 32 профилях Precision@5 = 0,675, NDCG@5 = 0,966 против 0,525 и 0,6425 у простого совпадения стека. Это авторская разметка синтетики, без реальных наймов и независимой внешней экспертизы.

Симуляция 1 200 профилей и 2 400 попыток дала 82,17% совпадения результата двух вариантов; для пограничных профилей лишь 49,75%. Короткий тест требует дальнейшей калибровки на реальных людях. Тёплый прогон версии 1.0.2 внутри Docker на Linux и Node.js 24.19.0: 100 запросов при параллелизме 20 завершился без ошибок: p50 84,7 мс, p95 142,5 мс, p99 142,7 мс. Маленький набор на localhost не доказывает производственную пропускную способность.

Полный протокол: [механика и валидация](docs/domain-mechanics.md), [числовой отчёт](docs/validation-results.json), [техническое описание](docs/technical-solution.md). Сохранённые результаты: [API](docs/api-validation.json), [приватность PDF](docs/pdf-validation.json), [локальная нагрузка](docs/load-validation.json). Раннеры сохраняют текущие прогоны в `tests/results/`.

## Архитектура и API

Модульный монолит: React/Vinext, серверные HTTP-обработчики, чистые доменные функции и D1. Сервер контролирует роль, владельца записи, подтверждение email, последнюю анкету, статус теста и отклика и разрешение на контакт. Ответы тестов никогда не передаются до отправки попытки. История исходной подборки хранится отдельно; последующее чтение проверяет актуальные согласия и скрывает контакты по новым правилам также в снимках прежней версии. Отзыв обработки закрывает работодателям карточку, PDF и контакты принятого приглашения; отзыв публикации допускает прежний согласованный диалог при действующем согласии на обработку.

- [Архитектура и данные](docs/architecture.md)
- [API и примеры](docs/api.md)
- [OpenAPI 3.1](public/openapi.json), доступен как `/openapi.json`
- [Проверка компетенций и формула подбора](docs/domain-mechanics.md)

JSON-успех имеет вид `{"data":...}`, ошибка — `{"error":{"code":"...","message":"..."}}`. Сессия — непрозрачный cookie `fsp_session`, HttpOnly, SameSite=Lax, Secure на HTTPS. Пароли — PBKDF2-SHA256 с индивидуальной солью; в MVP 100 000 итераций из-за ограничения native WebCrypto в Workers. Для промышленного размещения предусмотрен переход на внешний IdP или KDF с более высоким параметром затрат.

## Сборка и публикация

`npm run build` создаёт автономный Worker и статические ассеты в `dist/`. Docker сохраняет тот же backend и D1-схему в локальном CPU-эмуляторе. Для будущего внешнего стенда подготовлена [инструкция по размещению](docs/deployment-options.md): VM в Яндекс Cloud потребует проверки runtime за HTTPS-прокси; альтернативный вариант — native Worker с настоящей привязкой D1. Публичный хостинг сейчас не выполнялся. База находится на сервере, а browser localStorage не заменяет её. Регистрация, подтверждение email и вход реализованы собственными серверными обработчиками приложения.

При изменении схемы выполните `npm run db:generate`, проверьте SQL в `drizzle/`, затем примените миграции. Начальные строки данных создаются сервером отдельно от DDL, не в SQL-миграциях. Храните SQL и журнал Drizzle в репозитории. Обновление схемы и данных производственного стенда требует отдельного резервного копирования и проверки миграций.

Перед сдачей зафиксируйте commit/tag и соответствующее видео. После дедлайна функциональность сданной версии не меняют до разрешённого организаторами этапа. Сведения о составе команды и авторах в презентации заполняются командой.
