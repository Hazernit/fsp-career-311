# Стенд ФСП в Яндекс Cloud без собственного домена

Схема: браузер → служебный HTTPS-адрес API Gateway → приватный IPv4 отдельной Ubuntu 24.04 VM → один Docker-контейнер и постоянный том SQLite. Новый Compose project `fsp-career-cloud` и том `fsp-career-cloud-data` изолированы от других проектов. Не запускайте bootstrap на VM другого проекта.

## Подготовка ресурсов

1. Сверьте доступный грант, дату его окончания и расход существующего размещения до **31 октября 2026 года включительно**. Оставьте этот резерв вне бюджета ФСП. Грант и конфигурация в этой инструкции не обещают бессрочное бесплатное размещение.
2. Выберите отдельную непрерываемую VM: Ubuntu 24.04, 2 vCPU, 4 ГБ RAM, 30 ГБ SSD. CPU 20% подходит для малой демонстрации; сборка на нём будет медленнее. Не меняйте размер, диск или настройки действующего другого стенда.
3. Используйте существующую VPC, если в ней есть подсети во всех доступных AZ. В настройках Gateway выберите **эту же VPC**. Gateway создаёт служебные подсети `198.19.0.0/16`; без выбранной VPC приватный адрес VM недоступен. [Сеть API Gateway](https://yandex.cloud/ru/docs/api-gateway/concepts/networking).
4. Назначьте VM **отдельную** группу безопасности: входящий TCP 8080 только от `198.19.0.0/16`, TCP 22 только от административного IPv4 `/32`. Не добавляйте её к чужой VM и не редактируйте чужую группу. Исходящий доступ нужен для установки пакетов, GitHub, Docker Hub и DNS. Публичный IP VM используется для SSH; приложение привязано только к приватному IPv4.
5. Сначала можно создать Gateway с временным dummy-ответом `503`, чтобы получить его HTTPS-host. Затем подготовить VM, получить приватный IP и заменить спецификацию на `yandex-gateway.template.yaml`. Для root `/` и greedy `/{path+}` настроено перенаправление всех методов, заголовков и query. Это важно для cookie, CSS/JS, PDF, регистрации, подтверждения и фильтров. [HTTP integration](https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/http).

## Запуск

Публикуется проверенный исходный commit с файлами этой папки. Подставляйте **полный 40-значный SHA**, чтобы VM запускала проверенные исходники. Для `FSP_GATEWAY_TOKEN` создайте случайные 32 байта, представленные 64 hex-символами. Один и тот же токен используется в Gateway header `X-FSP-Gateway-Token` и в конфигурации контейнера. Он не нужен пользователю и не публикуется в README, release или отчётах.

В приватной копии cloud-init замените `REPLACE_COMMIT`, `REPLACE_GATEWAY_HOST`, `REPLACE_GATEWAY_TOKEN`. Передайте её новой VM как user-data и настройте собственный SSH-ключ через консоль. Секретная копия cloud-init не должна попасть в Git. Шаблон вызывает `bootstrap-yandex.sh` для Ubuntu 24.04: устанавливает Docker, берёт указанный commit, создаёт отдельный том и запускает Compose. Результат — маркер `FSP_DEPLOYMENT_READY` и `/var/lib/fsp-career/deployment-ready.txt`. Bootstrap и сама установка в облаке ещё должны быть проверены на созданной VM.

`runtime.env` хранится только на VM в `/etc/fsp-career` с правами 0600. Wrangler читает токен через secret binding из окружения; параметр `--var` с токеном и его печать в стартовом логе не используются. Worker перед обработкой запросов сверяет токен и восстанавливает URL по фиксированному HTTPS-origin. Клиентский `Origin` сохраняется, поэтому проверка CSRF продолжает работать; cookie и ссылка подтверждения получают внешнюю HTTPS-схему.

## Проверки после старта

- Проверить root, CSS/JS/шрифты, `/api/meta`, регистрацию, подтверждение, повторный вход, анкету, тест, вакансии, отклик и PDF по **внешнему HTTPS-адресу**.
- Проверить `fsp_session` и `fsp_demo_pair`: `HttpOnly`, `SameSite=Lax`, `Secure`; чужой Origin должен возвращать 403.
- Убедиться, что `PUBLIC_VM_IP:8080` недоступен, а запрос к приватному backend без gateway token отклоняется.
- Сохранить отдельный тестовый профиль, перезапустить только контейнер ФСП и подтвердить сохранность. Существующее другое приложение не перезапускать.
- Для согласованной резервной копии остановить только контейнер ФСП, скопировать весь том, запустить контейнер снова. Не использовать `down -v`, `volume prune` и очистку чужих ресурсов.

## Известные границы

Это демонстрационный Worker в `wrangler dev --local`, один экземпляр SQLite, демо-почта и демо-реестр ФСП. Функциональные данные сохраняются в постоянном томе, но промышленная эксплуатация требует отдельной архитектурной доработки.

HTTP integration пропускает ответ через Gateway. Лимит одного запроса/ответа — 2,5 МБ: прикладываемые видео и презентации остаются в GitHub/Yandex Disk, а отдельные собранные файлы приложения меньше лимита. [Лимиты API Gateway](https://yandex.cloud/ru/docs/api-gateway/concepts/limits).

Клиентские `CF-Connecting-IP`, `X-Forwarded-For` и `Forwarded` не доверяются и очищаются. Пока не подтверждено безопасное предоставление client IP HTTP-интеграцией, существующие ограничения аутентификации общие для шлюза: 60 демо-входов и 15 регистраций в час. Этого достаточно для небольшого жюри; это ограничение для публичного потока пользователей.

11 октября: 5 unit-тестов proxy guard, TypeScript, production build, Compose config и 11 проверок **реального локального Wrangler runtime** с отдельной временной базой прошли. Проверены внешняя HTTPS-схема, отказ без токена, чужой Origin, Secure-cookie, регистрация/подтверждение и последующий вход. Эти проверки не подтверждают работу сети, VPC, firewall или самого API Gateway — их проверяют после облачного запуска.
